# 04 · Research Workspace (Phase R)

## วัตถุประสงค์

`research/` คือพื้นที่ทดลอง — train model, research model, ลอง pipeline และ vibe กับ agent ได้เต็มที่ กฎมีน้อยและมีไว้ปกป้องแค่สองเรื่อง: **ผลต้องทำซ้ำได้** และ **ความยุ่งของงานทดลองต้องไม่รั่วไปที่ `apps/` กับ `packages/`**

> ML system ส่วนใหญ่เป็น glue code และ "dead experimental codepaths" คือหนี้ที่แพงที่สุด — Sculley et al., *Hidden Technical Debt in Machine Learning Systems* ดังนั้น research code ไม่ ship ตรง ต้อง promote (ข้อ 6)

---

## 1. โครงสร้าง — หัวข้อ → approach

แต่ละ folder ใต้ `research/` คือ **หัวข้อ** (เรื่องที่กำลังแก้) ข้างในมี **approach** ที่แข่งกันตอบคำถามเดียวกันวางเรียงกัน

```text
research/
├── ocr/                                 # หัวข้อ: พัฒนา model OCR
│   ├── README.md                        # คำถามของหัวข้อ + ตารางเทียบทุก approach
│   ├── paddleocr/
│   └── glm-ocr/
├── apperances/                          # หัวข้อ: ตรวจลักษณะภายนอกของแบตเตอรี่
│   ├── README.md
│   ├── template-matching/
│   ├── anomaly-detection/
│   ├── object-detection/
│   ├── linear-optimization/
│   └── agentic-pipeline/
└── <topic>/
```

โครงของ approach หนึ่งตัว:

```text
research/<topic>/<approach>/
├── README.md                # Question · Data · How to run · Results · Decision (ข้อ 2)
├── pyproject.toml หรือ venv/ # environment ของ approach (torch, CUDA, paddle ...)
├── Taskfile.yml             # task <approach>:<command>
├── <stage>/                 # data_preparation, preprocess, train, evaluate ...
│   ├── __init__.py
│   ├── __main__.py          # python -m <stage> <command>
│   ├── README.md            # stage นี้ทำอะไร, input/output
│   ├── results/             # output (gitignored; ใหญ่ → DVC)
│   └── tests/               # CPU-only, ไม่ต้องใช้ dataset
├── exp<N>_<slug>/           # ถ้า approach ต้องลองหลายรอบ: แต่ละรอบเป็น folder มีเลข
├── docs/                    # สรุป paper, ตารางผลละเอียด, เหตุผลการเลือก
└── repos/                   # upstream research code — clone, ไม่ commit
```

- ชื่อหัวข้อและ approach เป็น `kebab-case` สั้น ๆ บอกว่าทำอะไร (`glm-ocr`, `anomaly-detection`)
- ชื่อรอบทดลอง `exp<N>_<slug>` เลขเรียงต่อ ไม่ reuse เลข
- แต่ละ stage รันเดี่ยวได้ด้วย `python -m <stage>` และอ่าน input จาก `results/` ของ stage ก่อนหน้า
- environment หนัก ๆ (torch + CUDA) อยู่ระดับ approach หรือหัวข้อ ให้เรียกด้วย path เต็ม (`./venv/bin/python`) เพื่อไม่ให้ shell ที่ root ไปใช้ `.venv` ของ workspace โดยไม่รู้ตัว
- approach ที่เป็น pipeline รวมหลายเทคนิค (เช่น `agentic-pipeline/`) ก็เป็น approach ตัวหนึ่ง: copy ส่วนที่ต้องใช้จาก approach อื่นเข้ามา

## 2. Template README

**README ของหัวข้อ** (`research/<topic>/README.md`):

```markdown
# <topic>

## Question
<ปัญหาที่หัวข้อนี้แก้ + model acceptance metric ของ story>

## Approaches
| approach | best <metric> | latency (target GPU) | status |
|---|---|---|---|
| paddleocr | | | running / dropped / chosen |
```

**README ของ approach** (`research/<topic>/<approach>/README.md`):

```markdown
# <approach>

## Question
<คำถามเดียวที่ approach นี้ตอบ>

## Data
- dataset: <ชื่อ> @ <git commit ของไฟล์ .dvc>
- split: <train/val/test หรือ normal/defect และจำนวน>

## How to run
task <approach>:<command>     # ~เวลา, GPU/CPU

## Results
| run | <metric 1> | <metric 2> | latency (target GPU) | note |
|---|---|---|---|---|

## Decision
<วิธีที่ user เลือก + เหตุผล หรือ "open">
```

ตาราง Approaches ของหัวข้อคือ gate ของ Phase R — user เลือก approach จากตารางนี้

## 3. เริ่มงานใหม่ — แตก branch ก่อนเสมอ

ก่อนสร้างหัวข้อ, approach หรือรอบทดลองใหม่:

```bash
git fetch origin
git switch -c research/<topic>-<slug> origin/main     # เช่น research/ocr-glm-finetune
```

- หนึ่ง branch ต่อหนึ่งคำถาม; ผล (README, โค้ด, `run.log` เล็ก ๆ, `.dvc`) เข้า `main` ผ่าน PR
- ห้ามทำ experiment บน `main` หรือบน branch ของงานอื่น

## 4. กฎ (ทั้งหมดมีแค่นี้)

1. **หนึ่ง approach หนึ่ง folder** — ห้าม import ข้าม approach หรือข้ามรอบทดลอง ให้ **copy** สิ่งที่ต้องใช้มา การแก้ approach หนึ่งจึงไม่ทำให้ตัวเลขของอีกตัวเปลี่ยน
2. **ทิศทาง import:** `research → packages` ได้; `apps/` และ `packages/` ห้าม import `research/` เด็ดขาด
3. **ข้อมูลและ weights ผ่าน DVC** — git เก็บแค่ `.dvc`, README, โค้ด, `run.log` ขนาดเล็ก; `results/` ที่ใหญ่และ `repos/` อยู่ใน `.gitignore`
4. **ผลทำซ้ำได้** — ทุกตัวเลขใน README มาจาก task ที่รันได้, fix random seed, บันทึก dataset version
5. **lineage** — dataset ที่ทำขึ้นเอง (crop, split, synthetic) มีคอลัมน์ `_source_file`, `_batch_id`, `_processed_at`, `_pipeline_version` และไม่แก้ข้อมูลดิบ (ดู 03 ข้อ 10)
6. **test แบบ CPU-only** สำหรับ logic ที่ตัวเลขขึ้นกับมัน (metric, การ split, geometry) — ไม่ต้องครอบทุกอย่าง
7. **มาตรฐานโค้ด** — house rules (OOP, import module, 3 บรรทัดว่าง, signature + docstring) ใช้ใน research ด้วย; ที่ผ่อนได้: `print()` แทน `logging`, coverage, การแยก layer
8. **ห้ามแตะ production** — ใช้ model server ที่แชร์ได้ผ่าน HTTP เท่านั้น ห้าม publish ไป MQTT topic หรือเขียน DB ของ production

## 5. Vibe กับ Agent

- เริ่ม session โดยชี้ agent ไปที่ README ของหัวข้อและของ approach (และ `CONTEXT.md` ถ้ามี)
- ให้ agent วิจัยก่อนลงมือ: ค้น paper / repo ต้นฉบับ แล้วเขียนสรุปลง `docs/` ของ approach พร้อม URL
- งานยาว (train, align ทั้ง dataset) ให้ log ลงไฟล์ (`results/<run>/run.log`) เพื่อ `tail -f` ได้
- notebook (`.ipynb`) ใช้ `display()` และต้องรันจนมี output ก่อนบอกว่าเสร็จ
- ตัวเลขที่ agent รายงานต้องมาจากไฟล์ผลที่รันจริง ไม่ใช่ประมาณ

## 6. Promote: research → package → app

เมื่อ user เลือก approach แล้ว:

1. **แตก branch** `packages/<pkg-name>` จาก `main`
2. **เขียนใหม่ ไม่ย้าย** — rewrite เส้นทางที่เลือกเข้า `packages/<pkg>/src/<pkg>/` ทิ้ง branch ทดลอง, flag และ code path ที่ไม่ได้ใช้
3. **API เล็ก** — class เดียวหรือสองตัวที่ app เรียก เช่น `detector.StructuralDetector(...).score(image)` ซ่อน model loading และ preprocessing ไว้ข้างใน
4. **test เต็ม** — unit test ใน `packages/<pkg>/tests/unit_tests/` รวม regression test ที่ล็อกค่า acceptance metric บนชุดข้อมูลเล็กที่ track ด้วย DVC
5. **config ไม่ hardcode** — threshold, ขนาด canvas, path ของ weight มาจาก settings
6. **ต่อเข้า app** — use case ของ app เรียก package; ถ้า model รันเป็น server แยก ให้เป็น app (worker) ของตัวเอง และ app อื่นคุยกับมันผ่าน adaptor (HTTP / MQTT) ตาม `7.2_Clean_Architecture_Backend.md`
7. **container** — dependency ผ่าน `uv add --package`, weight ดึงตอน build หรือ mount, compose stack รันได้
8. **อ้างกลับ** — README ของ package บอกว่ามาจาก approach ไหนและได้ตัวเลขเท่าไร; README ของหัวข้อเปลี่ยน status เป็น `chosen`

## Quality gate (Phase R)

✅ ทำบน branch ของตัวเอง · ✅ README ของ approach มี Question · Data (+ version) · How to run · Results · Decision · ✅ README ของหัวข้อมีตารางเทียบ approach · ✅ ไม่มี import ข้าม approach · ✅ ไม่มี dataset / weight ใน git · ✅ ตัวเลขทุกตัวมาจาก task ที่รันซ้ำได้ · ✅ user เลือก approach แล้วก่อนเริ่ม promote
